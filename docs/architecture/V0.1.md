# Architecture V0.1

## High-level architecture

```text
                  Remote workstation / browser
                         |
                  SSH / HTTPS / LAN
                         |
                 +------------------+
                 |   LocalAI-Lab    |
                 |     Server       |
                 +------------------+
                         |
              Web control plane / API
                         |
             +-----------+-----------+
             |                       |
        Coding mode             Research mode
             |                       |
      Qwen3-Coder family        General Academic LLM
             |                       |
        Coding agent                 RAG
                                     |
                         Embeddings + Reranker
                                     |
                               Vector DB
```

A future Teaching Content Generator will be added only after the Academic stack and web control plane are stable. The first version is expected to reuse a validated general instruction model and the same document-grounding infrastructure rather than introducing a dedicated model prematurely.

## Hardware baseline

```text
Intel Core i5-14600KF
64 GB system RAM
AMD Radeon RX 9060 XT 16 GB
NVMe + dedicated model/data SSD storage
```

## Operating principle

Only one main LLM is expected to remain loaded at any given time. Supporting RAG components may remain active depending on measured memory consumption.

This rule also applies to future web-managed modes. Mode changes should stop the current large model, verify process termination and VRAM release, start the requested model profile, perform a health check, and only then report the new mode as READY.

## Planned service/control architecture

```text
Browser
  |
  v
FastAPI / HTML control panel
  |
  v
Mode / Service Manager
  |
  +--> Coding Agent profile
  |      -> llama-server
  |      -> Qwen3-Coder
  |
  +--> Academic Reviewer profile
  |      -> llama-server
  |      -> Qwen3 general instruction model
  |      -> RAG / retrieval services
  |
  +--> Future Teaching Content Generator
         -> grounded document retrieval
         -> general instruction model
         -> pedagogical planning
         -> structured content
         -> Markdown / PDF / PPTX renderers
```

The web interface is intended to control Linux backend services and model profiles. Client-side tools such as OpenCode remain on the Windows workstation and connect to the active backend over the LAN.

## Service transition model

The control plane should expose explicit state rather than treating process launch as immediate readiness:

```text
STOPPED
  -> STARTING
  -> READY
  -> STOPPING
  -> STOPPED

Any failed transition
  -> ERROR
```

Switching modes should use a serialized transition with a lock so that two large model profiles cannot be started concurrently by competing requests.

## Initial service concept

Possible service units or managed processes:

```text
localai-code.service
localai-research.service
localai-rag.service
localai-vector-db.service
localai-webui.service
```

A future teaching mode may reuse `localai-research.service` when the same general instruction model is appropriate, while adding separate retrieval/prompt/rendering profiles. A dedicated `localai-teaching.service` should only be introduced if it provides a measurable operational benefit.

The exact service layout will be refined after the current Academic experiments and benchmarked before being considered stable.

## Future Teaching Content Generator pipeline

The planned auxiliary is source-grounded rather than free-form-first:

```text
Books / articles / instructor texts
  -> extraction + metadata
  -> structure-aware chunks
  -> embeddings / retrieval
  -> evidence selected for the requested lesson
  -> general instruction LLM
  -> pedagogical plan
  -> structured lesson representation
  -> deterministic renderers
       -> Markdown
       -> PDF
       -> PPTX
```

Key design constraints:

- source analysis and pedagogical planning are separate stages;
- the LLM should produce structured content, not binary office/PDF files directly;
- references should survive from retrieved evidence through the intermediate representation into final material when appropriate;
- PPTX and PDF generation should be deterministic/template-driven after content generation;
- the initial model baseline should reuse Qwen3-30B-A3B-Instruct-2507 unless later benchmarks demonstrate that another general-purpose model is materially better;
- generation quality and file-rendering correctness should be evaluated separately.

## Observability requirement

Production services should expose structured logs and enough telemetry to associate a benchmark run with its model configuration, resource consumption and result.

Future Teaching Content experiments should additionally preserve:

- source-set identity and hashes where licensing permits;
- retrieval/chunk identifiers used for each generated artifact;
- prompt/profile version;
- intermediate structured representation;
- renderer/template version;
- final artifact metadata;
- unsupported-claim/hallucination evaluation;
- instructor editing effort where measured.
